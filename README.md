## Overview

The **Decentralized Healthcare Data Exchange Platform** is a proof-of-concept blockchain application that demonstrates how medical records can be managed with patient-controlled access on a decentralized network.

Instead of hospitals holding all control over patient data, this platform:
- Stores a **cryptographic SHA-256 hash** of each medical document on-chain — proving it exists and hasn't been tampered with — while the actual file stays off-chain.
- Lets **patients grant or revoke** a doctor's access to their records at any time via a smart contract transaction.
- Logs every access event, consent grant, and revocation as an **immutable on-chain audit trail** (Solidity events).
- Uses **wallet addresses** (MetaMask) as the identity layer — no usernames, no passwords.

---

## Problem Statement

The current centralized healthcare system suffers from four core problems:

| Problem | Impact |
|---|---|
| **Data Silos** | Records fragmented across hospitals; no unified patient history |
| **No Patient Control** | Institutions decide who accesses data; patients have no visibility |
| **Tampering Risk** | Centralized databases can be altered or deleted without a trace |
| **Poor Interoperability** | Incompatible EHR systems; records shared via fax/email |

This project demonstrates how a blockchain-based system can address each of these problems in a prototype context.

## Objectives

- Simulate patient-controlled medical record registration using on-chain hashes and off-chain dummy files
- Implement consent management (grant/revoke doctor access) via Solidity smart contract
- Verify access permissions on-chain before exposing any record metadata
- Generate an immutable, timestamped audit trail of all access events using Solidity events
- Build a React frontend with separate Patient Dashboard and Doctor Dashboard
- Demonstrate core Web3 concepts: wallet identity, smart contracts, events, mappings, modifiers, access control

## Smart Contract Functions

All functions are in [`contracts/HealthRecords.sol`](./contracts/HealthRecords.sol).

| Function | Who Can Call | Description |
|---|---|---|
| `registerDoctor(address)` | Admin only | Whitelists a wallet address as a verified doctor/hospital |
| `addRecord(address, bytes32, string, string)` | Patient or registered doctor | Stores record metadata + SHA-256 hash on-chain; emits `RecordAdded` |
| `grantAccess(address)` | Patient only | Gives a doctor global consent to access all records; emits `AccessGranted` |
| `revokeAccess(address)` | Patient only | Removes a doctor's consent immediately; emits `AccessRevoked` |
| `requestRecordAccess(address, uint256)` | Doctor (must have consent) | Verifies consent, returns record data, **emits `RecordAccessed` audit event** |
| `getMyRecords()` | Patient only (view) | Returns array of all records owned by `msg.sender` |
| `getRecord(uint256)` | Patient or consented doctor (view) | Returns a single record without logging an audit event |
| `hasAccess(address, address)` | Anyone (view) | Returns `true` if a doctor currently has consent from a patient |
| `getRecordCount()` | Anyone (view) | Returns total records registered in the contract |

### Events (Immutable Audit Trail)

| Event | Triggered By | Data Logged |
|---|---|---|
| `DoctorRegistered` | `registerDoctor` | doctorAddress, timestamp |
| `RecordAdded` | `addRecord` | recordId, patientAddress, uploadedBy, recordType, timestamp |
| `AccessGranted` | `grantAccess` | patientAddress, doctorAddress, timestamp |
| `AccessRevoked` | `revokeAccess` | patientAddress, doctorAddress, timestamp |
| `RecordAccessed` | `requestRecordAccess` | recordId, patientAddress, doctorAddress, timestamp |

## Consent Workflow

```
1. PATIENT calls grantAccess(doctorAddress)
   → consent[patient][doctor] = true
   → AccessGranted event emitted (permanent log)

2. DOCTOR calls requestRecordAccess(patientAddress, recordId)
   → Contract checks: consent[patient][doctor] == true?
   → YES: returns record data + emits RecordAccessed (audit event)
   → NO:  transaction REVERTS — "access not authorized"

3. PATIENT calls revokeAccess(doctorAddress)
   → consent[patient][doctor] = false
   → AccessRevoked event emitted (permanent log)
   → Doctor's next requestRecordAccess call will be rejected
```

## How To Run

### Prerequisites
- Node.js v18+ and npm
- MetaMask browser extension installed
- Git (optional)

### Step 1 — Install root dependencies (Hardhat)
```bash
npm install
```

### Step 2 — Compile the smart contract
```bash
npx hardhat compile
```

### Step 3 — Run the test suite
```bash
npx hardhat test
```

### Step 4 — Start a local Hardhat blockchain node
```bash
npx hardhat node
```
> Keep this terminal open. Copy one of the private keys shown — you'll need it for MetaMask.

### Step 5 — Deploy the contract (new terminal)
```bash
npm run deploy
```
> This automatically writes `frontend/src/contract-config.js` with the deployed address and ABI.

### Step 6 — Set up MetaMask
1. Open MetaMask → Add a network → Localhost 8545 (Chain ID: 31337)
2. Import account → Paste a private key from the `npx hardhat node` output
3. Repeat for a second account (to test patient vs. doctor)

### Step 7 — Install and run the frontend
```bash
cd frontend
npm install
npm run dev
```
> Opens at [http://localhost:5173](http://localhost:5173)

## Results

The working prototype demonstrates:

1. **Patient-controlled consent** — Only a patient can grant or revoke a doctor's access. No central authority has override capability.
2. **Hash-based integrity** — SHA-256 hashes stored on-chain can be recomputed from off-chain files at any time to verify they haven't been tampered with.
3. **Immutable audit trail** — Every `RecordAccessed` event is permanently logged. Even after revocation, historical access events remain on-chain forever.
4. **Access enforcement** — The smart contract's `require()` statements prevent any unauthorized access — even if the doctor knows the record ID, the transaction reverts without consent.
5. **Role separation** — Admin, patient, and doctor roles are enforced by `msg.sender` checks and mappings, not by a database.

## Security Considerations

- **On-chain data is public** — Everything stored on a blockchain is visible to anyone. Never store real patient names, diagnoses, or other sensitive data on-chain. This prototype stores only hashes and metadata (record type, file reference), which are kept non-identifying.
- **Hashes prove integrity, not confidentiality** — A SHA-256 hash proves a file hasn't changed. It does NOT protect the file contents from being read. In a real system, off-chain files must be encrypted before storage.
- **No real identity verification** — Wallet addresses are pseudonymous. In production, a DID (Decentralized Identifier) system would be needed to link wallets to verified clinical identities.
- **Local blockchain has no real economic security** — The Hardhat local network is purely for development. There is no mining, no real ETH, and no real Sybil resistance.
- **Never commit private keys** — The `.gitignore` excludes `.env` files. Use environment variables for any real deployment keys.

---

## Limitations

- **Not HIPAA/GDPR compliant** — No audit controls for covered entities, no breach notification, no data subject rights implementation.
- **No real identity verification** — Any wallet can claim to be a patient or doctor. A real system would require credential verification (medical license check, patient identity proof).
- **No encryption of off-chain files** — In this prototype, the dummy files in `offchain-storage/` are plain JSON. A production system must encrypt files before storing them on IPFS or any server.
- **Global consent model** — Granting access to a doctor gives them access to ALL records. A production system would need per-record consent granularity.
- **Off-chain storage is simulated** — Files are stored locally. A real system would use encrypted IPFS or a hospital's private server with access logs.
- **No key management** — Private keys are managed by MetaMask with Hardhat test accounts. Real key management would require HSMs or multi-sig.

## Future Improvements

- **Real IPFS integration with encryption** — Files encrypted with the patient's public key before upload; hash stored on-chain; doctor decrypts with patient-shared key after consent.
- **DID-based identity verification** — Use W3C Decentralized Identifiers (DIDs) to link wallet addresses to verified clinical identities (e.g., Verifiable Credentials for medical licenses).
- **Per-record consent** — Instead of global consent, patients could approve specific records for specific doctors, with optional expiry timestamps.
- **Emergency access override** — Allow a pre-approved emergency contact or next-of-kin to access records in emergencies, with automatic audit logging.
- **Layer 2 / lower gas costs** — Deploy on a Layer 2 network (Polygon, Arbitrum) to reduce gas costs for real-world use.
- **Mobile application** — React Native app with WalletConnect integration for mobile patients and doctors.
